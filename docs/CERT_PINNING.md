# Certificate Pinning Setup

Certificate pinning makes the mobile app refuse connections that don't present a known leaf certificate, preventing man-in-the-middle attacks even on networks where the attacker has installed a custom root CA (corporate Wi-Fi, malware proxy, nation-state DPI).

> **Cost of pinning:** if your TLS cert rotates and you forget to update the pin in time, every installed app stops connecting. **Always pin two values: the current cert AND the next planned cert.** Read the rotation runbook below before enabling.

## Status

Pinning is **NOT yet enabled** in Zeitra. This doc is the setup guide. Apple's `NSPinnedDomains` (iOS 14+) and Android's `network_security_config.xml` are both supported natively without any new dependencies — the only blocker is producing the pin values, which require your live cert.

---

## 1. Get your SPKI hash

You pin the hash of the certificate's **Subject Public Key Info (SPKI)**, NOT the cert itself. SPKI hashes survive cert renewal as long as you keep the same key — preventing accidental lockout when LetsEncrypt rotates your leaf every 90 days.

### Step 1 — Pull your live cert

```bash
echo | openssl s_client -servername api.zeitra.app -connect api.zeitra.app:443 2>/dev/null \
  | openssl x509 -outform PEM > current-cert.pem
```

### Step 2 — Compute the SPKI SHA-256 hash

```bash
openssl x509 -in current-cert.pem -pubkey -noout \
  | openssl pkey -pubin -outform DER \
  | openssl dgst -sha256 -binary \
  | openssl enc -base64
```

You'll get something like `eXamplE12+abc/def==xyz=`. **That's your pin.**

### Step 3 — Generate a backup pin

You need at least one backup so you don't brick the app on cert rotation. Generate a new private key + CSR for the next cert, hash *its* public key with the same pipeline, and use that as the second pin. You can pre-load multiple backup pins.

```bash
openssl genrsa -out backup-key.pem 2048
openssl rsa -in backup-key.pem -pubout -outform DER \
  | openssl dgst -sha256 -binary \
  | openssl enc -base64
```

Store `backup-key.pem` somewhere VERY safe (1Password / Vault). When the current cert rotates, sign the next cert with this key.

## 2. iOS — `NSPinnedDomains`

Built into Apple's App Transport Security since iOS 14. No third-party library needed.

Add to `clients/mobile/app.json`:

```json
"ios": {
  "infoPlist": {
    "NSAppTransportSecurity": {
      "NSAllowsArbitraryLoads": false,
      "NSPinnedDomains": {
        "api.zeitra.app": {
          "NSIncludesSubdomains": false,
          "NSPinnedCAIdentities": [
            {
              "SPKI-SHA256-BASE64": "<paste-current-pin-here>"
            },
            {
              "SPKI-SHA256-BASE64": "<paste-backup-pin-here>"
            }
          ]
        }
      }
    }
  }
}
```

Run `eas build --platform ios --profile preview` after this change. Test against the live API. Then test against an attacker proxy (mitmproxy with a self-signed root) — the connection should fail.

## 3. Android — `network_security_config.xml`

Create `clients/mobile/android/app/src/main/res/xml/network_security_config.xml` (the `android/` dir is generated by `expo prebuild`):

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <domain-config>
        <domain includeSubdomains="false">api.zeitra.app</domain>
        <pin-set expiration="2027-01-01">
            <pin digest="SHA-256"><paste-current-pin-here></pin>
            <pin digest="SHA-256"><paste-backup-pin-here></pin>
        </pin-set>
    </domain-config>
</network-security-config>
```

Then point `AndroidManifest.xml` at it (this is automatic if you set `usesCleartextTraffic: false` in app.json). After `eas prebuild`, verify the manifest entry.

> **Set `expiration` ~12 months out.** Android *requires* an expiration — when it lapses, pinning auto-disables (a safety hatch against bricking). Calendar a renewal reminder for `expiration - 30 days`.

## 4. Rotation runbook

When your TLS cert rotates:

1. **Generate the new cert with your backup key** (the one you generated in Step 1.3 above). The pin still matches because we pinned the SPKI, not the cert.
2. **Generate a new backup key** for the *next* rotation. Hash its public key. This is the new "backup pin."
3. **Ship a mobile release** that updates the pin set:
   - Old pin (still valid until cert actually rotates)
   - Current backup pin (now becomes "current pin" after rotation)
   - New backup pin
4. **Wait for >90% of installed-base adoption** of the new release before doing the actual cert rotation. Use Sentry releases dashboard to track.
5. **Rotate the cert.** Old apps still work because their pin matches the previous cert; new apps work because they have the new pin.
6. **Drop the old pin** in the next release after rotation. Now you're back to current-pin + new-backup-pin.

This is a forced 30-day cycle minimum. Don't try to rotate without a slow rollout — you will brick installed apps.

---

## 5. Emergency disable

If pinning brickedanybody (despite all the precautions): the only fix is a new app release without the pin, or with the new pin. **There is no remote disable.**

This is why we ship pinning behind a feature flag in `app.json` with a clear path to re-issue if needed. Keep at least one team member's mac signed in to App Store Connect with cert + key + 2FA codes off-network at all times.

---

## 6. Why no third-party SDK?

Earlier versions of this project considered `react-native-ssl-pinning` and `react-native-cert-pinner`. We chose the platform-native approach because:

1. **No native dependency to maintain** — Apple and Google update their pinning infrastructure as part of OS updates; a third-party SDK is one more thing to bump.
2. **Pinning is a TLS-layer concern**, not an HTTP-library concern. Native ATS / NSC enforces it for *every* connection (including WebSockets, third-party SDKs phoning home, etc.) — a JS-level axios pin only catches axios traffic.
3. **One less surface for a malicious dependency** — supply-chain attacks on RN packages are common.

The trade-off is that pinning errors don't surface as a regular `axios` error — they fail at the TLS handshake and propagate as a network error with `code: 'ENETUNREACH'` (or similar). Sentry will log them; pin breakage is rare enough that the lower observability isn't a real cost.

## 7. Testing checklist before shipping

- [ ] Build a preview with the new pin set
- [ ] Connect to your real API — works
- [ ] Connect through mitmproxy with a custom CA — **must fail**
- [ ] Connect through Charles with a custom root cert — **must fail**
- [ ] Force-stop & re-open the app on cellular to verify cold-path works
- [ ] Run on a corporate Wi-Fi (school, office, coffee chain) — works
- [ ] Sentry release tagged correctly so you can roll back if pinning surfaces unexpected breakage
